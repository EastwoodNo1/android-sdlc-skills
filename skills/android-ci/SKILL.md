# android-ci

Templates sit in `${CLAUDE_SKILL_DIR}/templates/` and are byte copies of SuperSnake. They record what was verified on the day they were made. Do not trust them: re-verify every version and SHA below on the day you use them. Show the evidence named in each step. Work through the steps without stopping to ask, except that step 6 (anything outward-facing) needs the owner's approval: do it only when it was given, otherwise say it was skipped.

Command hygiene: type literal absolute paths (`${CLAUDE_SKILL_DIR}` is already expanded in this text) instead of shell variables or loops, run one lookup per command, and save downloads under `build/tmp/` in the project so permission rules and sandboxes can match them.

## Steps

1. Re-verify the pins. For each item, run the command, show its output, and compare with the template. If a newer stable exists, use it and record it in `docs/versions.md` (item, version, release date, source URL, date verified).
   - `actions/checkout`, `gradle/actions` (setup-gradle), `github/codeql-action` (init, analyze): `gh api repos/<owner>/<repo>/releases/latest` (codeql-action: list the `v4.x` releases, since latest returns the bundle tag) and `gh api repos/<owner>/<repo>/git/ref/tags/<tag>`. If the object type is `tag`, dereference it with `git/tags/<sha>` to the commit SHA. Workflows use the full commit SHA.
   - mise: latest release tag, then `curl -fsSL <release>/SHASUMS256.txt`, the linux-x64 archive line, and `gh attestation verify <archive> --repo jdx/mise`. The version and SHA-256 are written in three places (`checks` and `pr-rules` in ci.yml, `java-kotlin` in codeql.yml). Update all three together.
   - zizmor: latest stable from https://github.com/zizmorcore/zizmor/releases (not a pre-release). Also gh, Gradle (`https://services.gradle.org/versions/current`, wrapper SHA-256), Temurin (Adoptium API) and ktlint (Maven metadata). Update `mise.toml`, then run `mise lock` and `mise install --locked`.
   - Kotlin cap: Kotlin may only be as new as CodeQL lists at https://codeql.github.com/docs/codeql-overview/supported-languages-and-frameworks/. Fetch the page with WebFetch, or save it with `curl -fsSL -o <file> <url>` and `grep -i kotlin <file>` (delete the file afterwards). Evidence: the supported-version line you read.
2. Copy the templates: `.github/workflows/*`, `.github/dependabot.yml`, `.github/pull_request_template.md`, `SECURITY.md`, `mise.toml`, `mise.lock`, `.editorconfig`, `scripts/github/*`, `scripts/check-ui-test-results.sh`, `gradle/ktlint.gradle.kts`, `build-logic/checks/**`, and `scripts/gradle-strict.sh` (from the git-hooks templates). Evidence: `git status --short`.
3. Wire Gradle. `${CLAUDE_SKILL_DIR}/reference/build.gradle.kts` and `${CLAUDE_SKILL_DIR}/reference/libs.versions.toml` are SuperSnake's project files, kept as references and not verified for drift: merge what the project needs, do not copy them over.
   - `settings.gradle.kts`: `includeBuild("build-logic/checks")`.
   - Root build: the `checks` configuration, `:checkNoComments`, `:checkCommitMessage`, `:checkCommitMessages`, `:checkPullRequest*`, `:checkWorkflows`, `:checkReleaseManifest` and `:checkBackupRules` (both only if there is an app module) and `apply(from = "gradle/ktlint.gradle.kts")`. `:checkTestsChanged` takes the module names whose `src/main` needs `src/test`.
   - `:checkBackupRules` runs `BackupRules` over the project's backup XML files (`full-backup-content`, `cloud-backup` and `device-transfer` sections). In the root build set `backupRuleFiles` (for example `app/src/main/res/xml/backup_rules.xml` and `data_extraction_rules.xml`) and `backupAllowedPaths`, the exact set of `include` paths the rules may contain (for example `datastore/settings.txt`). The check is registered with the arguments `backup-rules <allowed paths, comma separated> <files...>` and is a dependency of `check`. It fails when a file is not valid XML or has no backup section, when an `include` has a path outside the allowed set or a domain other than `file`, or when an allowed path is missing from a section. `SecureXml` parses the XML with external entities disabled; `ManifestHardening` uses it too.
   - Catalog: `kotlin`, `kover`, `junitBom`, `ktlint` versions and the `junit-bom`, `junit-jupiter`, `junit-platform-launcher`, `ktlint-cli` libraries, because `build-logic/checks/settings.gradle.kts` reads `gradle/libs.versions.toml`.
   - Always call root tasks with a leading colon (`:checkNoComments`), because AGP registers same-named tasks in `:app`.
4. Adapt the workflows to the project: SDK platform and build-tools in the `sdkmanager` line, the release build task, and the project's Gradle tasks. Keep: top-level `permissions: {}`, per-job least permissions, `persist-credentials: false`, actions pinned by full SHA, event data passed through `env:` only, no `pull_request_target` or `workflow_run`. Job names `checks`, `pr-rules`, `analyze (java-kotlin)`, `analyze (actions)` and `ui-tests (phone-31)` are the required checks. In `checks`, the release build is followed by an `R8 mapping exists` step and a 16 KB page alignment step, `zipalign -c -P 16 -v 4 <release apk>` from the SDK build-tools, which fails if any native library is not aligned to 16 KB.

   The `ui-tests` job runs `:app:connectedDebugAndroidTest` on an emulator matrix with `fail-fast: false`: `phone-37` and `tablet-37` on API 37.0 with the `google_atd` x86_64 image, and `phone-31` on API 31 with `google_apis`. Each leg runs the guard step "Require executed tests", `scripts/check-ui-test-results.sh [results dir]`, which exits non-zero when no `TEST-*.xml` exists, when any suite ran zero tests, or when any suite has a failure or an error, then uploads the result directories as an artifact named `ui-tests-<name>` (`if: always()`). Only the `phone-31` leg is required. Keep a leg informational, by leaving it out of the required checks in both `apply-repo-settings.sh` and `expected-settings.json`, while its emulator image is unstable (the API 37 x86_64 CI image crashes) and promote it once fixed. Adjust the matrix and API levels to the project, and drop the job for a project without instrumented tests. No comments in any yml, sh, kts, toml, xml.
5. Verify locally and show output: `mise exec -- zizmor .github/` with zero findings and no suppressions, then `ANDROID_HOME=<sdk> mise exec -- scripts/gradle-strict.sh check :checkNoComments :checkWorkflows`. Both must succeed. Add `gradle/verification-metadata.xml` with `./gradlew --write-verification-metadata sha256 check`, then strip any comments the tool wrote and re-run `:checkNoComments`.
6. Repo settings, only after the owner approves the outward step. Create the repo, push the initial commit to `main` first, then run `scripts/github/apply-repo-settings.sh <owner>/<repo>`. It applies squash-only merge (PR title and commit messages), the ruleset on the default branch (PR required, no bypass, linear history, conversation resolution, strict required checks), secret scanning with push protection, Dependabot alerts, private vulnerability reporting, a read-only default token and fork-PR approval, then compares the result with `expected-settings.json` and prints `all settings match`. Edit the required check names in both files if the workflow job names differ. Evidence: that output. Do not create a remote for a throwaway project.
7. Open the first PR. Its title is a Conventional header of at most 64 characters, its body has `Closes #<issue>` and a filled `## Evidence`. Wait for all required checks, then `gh pr merge <n> --squash`. Evidence: the CI run URL.

## Dependabot pull requests

A Dependabot PR only starts the work. Before it can merge, add commits that regenerate `gradle/verification-metadata.xml` (`./gradlew --write-verification-metadata sha256 check :app:assembleRelease :checks:check` with a fresh `GRADLE_USER_HOME` and `--refresh-dependencies`; add Linux-only artifacts such as the `aapt2` linux jar by hand after comparing SHA-1 with Google's `.sha1`), update `docs/versions.md`, and fill in Evidence. Strip tool-written comments. There are no bot exceptions. A Kotlin bump beyond the CodeQL-supported version stays open.

## Keeping in sync

`${CLAUDE_PLUGIN_ROOT}/scripts/verify-templates.sh <project>` prints one `drift:` line per differing file and `N drift`, exiting 1 on drift.
