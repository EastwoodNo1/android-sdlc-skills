# android-ci

Templates sit in `${CLAUDE_SKILL_DIR}/templates/` and record what was verified on the day they were made. Do not trust them: re-verify every version and SHA below on the day you use them. Show the evidence named in each step. Work through the steps without stopping to ask, except that step 6 (anything outward-facing) needs the owner's approval: do it only when it was given, otherwise say it was skipped.

Command hygiene: type literal absolute paths (`${CLAUDE_SKILL_DIR}` is already expanded in this text) instead of shell variables or loops, run one lookup per command, and save downloads under `build/tmp/` in the project so permission rules and sandboxes can match them.

## Steps

1. Re-verify the pins. For each item, run the command, show its output, and compare with the template. If a newer stable exists, use it and record it in `docs/versions.md` (item, version, release date, source URL, date verified).
   - `actions/checkout`, `gradle/actions` (setup-gradle), `github/codeql-action` (init, analyze), `actions/upload-artifact`, `actions/download-artifact`, `actions/create-github-app-token`, `googleapis/release-please-action`, `actions/attest`, `ReactiveCircus/android-emulator-runner`: `gh api repos/<owner>/<repo>/releases/latest` (codeql-action: list the `v4.x` releases, since latest returns the bundle tag) and `gh api repos/<owner>/<repo>/git/ref/tags/<tag>`. If the object type is `tag`, dereference it with `git/tags/<sha>` to the commit SHA. Workflows use the full commit SHA.
   - mise: latest release tag, then `curl -fsSL <release>/SHASUMS256.txt`, the linux-x64 archive line, and `gh attestation verify <archive> --repo jdx/mise`. The version and SHA-256 are written in nine places: `checks`, `ui-tests`, `release-smoke` and `pr-rules` in ci.yml, `build`, `smoke`, `sign-publish` and `verify-published` in release.yml, and `java-kotlin` in codeql.yml. Update all nine together (`grep -n MISE_ .github/workflows/*.yml`).
   - zizmor: latest stable from https://github.com/zizmorcore/zizmor/releases (not a pre-release). Also gh, Gradle (`https://services.gradle.org/versions/current`, wrapper SHA-256), Temurin (Adoptium API) and ktlint (Maven metadata). Update `mise.toml`, then run `mise lock` and `mise install --locked`.
   - Kotlin cap: Kotlin may only be as new as CodeQL lists at https://codeql.github.com/docs/codeql-overview/supported-languages-and-frameworks/. Fetch the page with WebFetch, or save it with `curl -fsSL -o <file> <url>` and `grep -i kotlin <file>` (delete the file afterwards). Evidence: the supported-version line you read.
2. Copy the templates: `.github/workflows/*` (ci.yml, codeql.yml, release.yml), `.github/dependabot.yml`, `.github/pull_request_template.md`, `SECURITY.md`, `mise.toml`, `mise.lock`, `.editorconfig`, `release-please-config.json`, `scripts/github/*`, `scripts/check-ui-test-results.sh`, `scripts/test-ui-test-guard.sh`, the release scripts (`scripts/check-release-ref.sh`, `sign-apk.sh`, `sign-throwaway.sh`, `verify-signature.sh`, `publish-release.sh`, `release-smoke.sh`, `test-release-scripts.sh`), `gradle/ktlint.gradle.kts`, `build-logic/checks/**`, and `scripts/gradle-strict.sh` (from the git-hooks templates). Evidence: `git status --short`.

   Then create the project-owned files, which are never templates because their values belong to the project:
   - `version.txt` with `0.0.0` and `.release-please-manifest.json` with `{".": "0.0.0"}`. release-please bumps both from then on.
   - `scripts/github/project-settings.json`, the input for `apply-repo-settings.sh`: `release_reviewer_user_id` (the GitHub user id of the person who approves signing, `gh api users/<login> --jq .id`) and `release_app_id` (the release GitHub App's numeric App id, not its client id), plus the optional `main_bypass_actors`: the bypass list of the ruleset on the default branch, default an empty list. Each item is `{"actor_id": <positive integer>, "actor_type": "RepositoryRole" | "Team" | "Integration" | "OrganizationAdmin" | "DeployKey", "bypass_mode": "always" | "pull_request" | "exempt"}`; for example `{"actor_id": 5, "actor_type": "RepositoryRole", "bypass_mode": "pull_request"}` lets repository admins merge a pull request without the rules while direct pushes stay blocked. Start from `${CLAUDE_SKILL_DIR}/reference/project-settings.json`, whose zeros are placeholders: the script exits 2 until both ids are positive integers, and also exits 2 when `main_bypass_actors` is not a list of valid items. The owner supplies the values and decides any bypass.
3. Wire Gradle. `${CLAUDE_SKILL_DIR}/reference/build.gradle.kts` and `${CLAUDE_SKILL_DIR}/reference/libs.versions.toml` are example project files, kept as references: merge what the project needs, do not copy them over.
   - `settings.gradle.kts`: `includeBuild("build-logic/checks")`.
   - Version: `versionCode = major*1_000_000 + minor*1_000 + patch` from `version.txt` (`VersionCode.of`, limits major ≤ 2099 and minor, patch ≤ 999, `0.0.0` maps to 1, a malformed or over-limit version fails the build). The root build imports `sdlc.checks.VersionCode`, declares `buildscript { dependencies { classpath("sdlc:checks") } }`, reads `version.txt` with `providers.fileContents` and sets `extra["versionName"]` and `extra["versionCode"]`; `:app` sets `versionCode = rootProject.extra["versionCode"] as Int` and `versionName = rootProject.extra["versionName"] as String`. The classpath sits in the root build because Lint's `UseTomlInstead` flags it in `:app`. See the reference build.
   - Root build: the `checks` configuration, `:checkNoComments`, `:checkCommitMessage`, `:checkCommitMessages`, `:checkPullRequest*`, `:checkWorkflows`, `:checkReleaseManifest` and `:checkBackupRules` (both only if there is an app module) and `apply(from = "gradle/ktlint.gradle.kts")`. `:checkTestsChanged` takes the module names whose `src/main` needs `src/test`.
   - `:checkBackupRules` runs `BackupRules` over the project's backup XML files (`full-backup-content`, `cloud-backup`, `device-transfer` and `cross-platform-transfer` sections). In the root build set `backupRuleFiles` (for example `app/src/main/res/xml/backup_rules.xml` and `data_extraction_rules.xml`) and `backupAllowedPaths`, the exact set of `include` paths the rules may contain (for example `datastore/settings.txt`). The check is registered with the arguments `backup-rules <allowed paths, comma separated> <files...>` and is a dependency of `check`. It fails when a file is not valid XML or has no backup section, when a `data-extraction-rules` file lacks `cloud-backup` or `device-transfer`, when an `include` path is empty or duplicated, when the allowed-paths argument is empty, when an `include` has a path outside the allowed set or a domain other than `file`, or when an allowed path is missing from a section. `SecureXml` parses the XML with external entities disabled; `ManifestHardening` uses it too.
   - Catalog: `kotlin`, `kover`, `junitBom`, `ktlint` versions and the `junit-bom`, `junit-jupiter`, `junit-platform-launcher`, `ktlint-cli` libraries, because `build-logic/checks/settings.gradle.kts` reads `gradle/libs.versions.toml`.
   - Always call root tasks with a leading colon (`:checkNoComments`), because AGP registers same-named tasks in `:app`.
4. Adapt the workflows to the project: SDK platform and build-tools in the `sdkmanager` line, the release build task, and the project's Gradle tasks. Keep: top-level `permissions: {}`, per-job least permissions, `persist-credentials: false`, actions pinned by full SHA, event data passed through `env:` only, no `pull_request_target` or `workflow_run`. Job names `checks`, `pr-rules`, `analyze (java-kotlin)`, `analyze (actions)`, `ui-tests (phone-31)`, `ui-tests (phone-37)`, `ui-tests (tablet-37)` and `release-smoke` are the required checks. Every job that runs Gradle, including `analyze (java-kotlin)` in codeql.yml, has a `setup-gradle` step (`:checkWorkflows` flags a workflow that runs `gradlew` or `gradle-strict.sh` without one). Only the `checks` job writes the Gradle cache: every `setup-gradle` step sets `cache-read-only: ${{ github.job != 'checks' }}`, and `checks` runs `:app:assembleDebugAndroidTest :app:connectedDebugAndroidTest --dry-run` to warm the instrumented-test dependencies. The SDK platform is `android-37.2` (compileSdk 37.2) and must match `scripts/bootstrap.sh`. `checks` also runs the release script tests, `scripts/test-release-scripts.sh <unsigned release apk>`. `pr-rules` exempts PRs labelled `autorelease: pending` or `autorelease: tagged` (the release PR, whose body release-please rewrites) from the issue-link and Evidence rules. In `checks`, the release build is followed by an `R8 mapping exists` step and a 16 KB page alignment step, `zipalign -c -P 16 -v 4 <release apk>` from the SDK build-tools, which fails if any native library is not aligned to 16 KB.

   The `ui-tests` job runs `:app:connectedDebugAndroidTest` on an emulator matrix with `fail-fast: false`: `phone-37` and `tablet-37` on API 37.0 and `phone-31` on API 31, all with the `google_apis` x86_64 image and an AVD `target=` fix in `pre-emulator-launch-script`. Each leg runs the guard step "Require executed tests", `scripts/check-ui-test-results.sh [results dir]`, which exits non-zero when no `TEST-*.xml` exists, when any suite ran no test that was not skipped, or when any suite has a failure or an error, then uploads the result directories as an artifact named `ui-tests-<name>` (`if: always()`, missing files fail the upload step). `checks` runs the guard's own tests, `scripts/test-ui-test-guard.sh`. All three legs are required checks, in both `apply-repo-settings.sh` and `expected-settings.json`. Adjust the matrix and API levels to the project, and drop the job for a project without instrumented tests.

   Run instrumented tests under the AndroidX Test Orchestrator, so each test runs in its own instrumentation process and one wedged test cannot time out every later test of the leg and burn the job limit. In the app module: `android { testOptions { execution = "ANDROIDX_TEST_ORCHESTRATOR" } }` and `dependencies { androidTestUtil(libs.androidx.test.orchestrator) }`, with the catalog entries `testOrchestrator` and `androidx-test-orchestrator` from the reference catalog. It is a test-only dependency: record it in `docs/versions.md` and regenerate `gradle/verification-metadata.xml`. Expect it to add about 3 to 6 minutes per leg (one project measured 12m48s, 16m27s and 19m25s on its three legs, against about 10 to 13 minutes before), and keep the job's `timeout-minutes` above that.

   The `release-smoke` job builds `:app:assembleRelease` (R8), signs it with a throwaway key (`scripts/sign-throwaway.sh`, a two-day PKCS12 key made and deleted in the run), and runs `scripts/release-smoke.sh` on an API 31 `google_apis` emulator. The script reads the package from the APK with `aapt2` (or `PACKAGE`), installs it, starts `.MainActivity`, taps the system "Got it" prompt if shown, taps `Play`, waits for `Game over. Score` and fails on no interaction, a timeout (`SMOKE_TIMEOUT_SECONDS`, default 120) or any `FATAL EXCEPTION` in logcat; evidence goes to the `release-smoke` artifact. The UI driving (activity name, `Play`, `Resume`, the game-over text) is specific to the app it was written for: adapt those lines and the fixtures in `test-release-scripts.sh` to the project's own start-to-done path, and accept that those two files then differ from the templates. No comments in any yml, sh, kts, toml, xml.
5. Verify locally and show output: `mise exec -- zizmor .github/` with zero findings and no suppressions, then `ANDROID_HOME=<sdk> mise exec -- scripts/gradle-strict.sh check :checkNoComments :checkWorkflows`. Both must succeed. Add `gradle/verification-metadata.xml` with `./gradlew --write-verification-metadata sha256 check`, then strip any comments the tool wrote and re-run `:checkNoComments`.
6. Repo settings, only after the owner approves the outward step, and the owner runs the script. Create the repo, push the initial commit to `main` first, then run `scripts/github/apply-repo-settings.sh <owner>/<repo>`. It applies squash-only merge (PR title and commit messages), the ruleset on the default branch (PR required, bypass only for the `main_bypass_actors` in `project-settings.json`, none by default, linear history, conversation resolution, strict required checks), the `release-tags` ruleset on `refs/tags/v*` (creation, update, deletion and force-push blocked, the release App as the only bypass actor), the environments `release-please` (`main` only, no reviewer) and `release` (`main` only, the release reviewer required, no admin bypass), the labels `autorelease: pending` and `autorelease: tagged`, immutable releases, secret scanning with push protection, Dependabot alerts, private vulnerability reporting, a read-only default token and fork-PR approval, then compares the result with `expected-settings.json` and prints `all settings match`. `--check <owner>/<repo>` only reads and compares. `--print-expected` prints `expected-settings.json` merged with `project-settings.json` and needs no `gh`. `expected-settings.json` carries 0 for both ids; the script fills them from `project-settings.json` (override the path with `PROJECT_SETTINGS`). Edit the required check names in `expected-settings.json` if the workflow job names differ. Evidence: that output. Do not create a remote for a throwaway project.
7. Open the first PR. Its title is a Conventional header of at most 64 characters, its body has `Closes #<issue>` and a filled `## Evidence`. Wait for all required checks, then `gh pr merge <n> --squash`. Evidence: the CI run URL.

## Live required checks

GitHub enforces the required checks of the live `main-protection` ruleset, not the list in `scripts/github/expected-settings.json`. They match only after the owner has run `apply-repo-settings.sh` with the current file. Until then, a check added to the file (a new UI-test leg, say) does not block the merge button, and squash auto-merge can merge a PR while that check is pending or red.

Before relying on auto-merge, and before calling a PR done, compare the two. All three commands only read:

```bash
gh api repos/<owner>/<repo>/rulesets --jq '.[] | select(.name == "main-protection") | .id'
gh api repos/<owner>/<repo>/rulesets/<id> --jq '[.rules[] | select(.type == "required_status_checks") | .parameters.required_status_checks[].context] | sort'
jq '[.ruleset.required_status_checks.required_status_checks[].context] | sort' scripts/github/expected-settings.json
```

- They match: the required checks are enforced; still report every check by name.
- They differ: do not enable auto-merge. Wait for every check on the PR (`gh pr checks <n> --watch`), not only the required ones, and report each by name with its result before merging or calling the PR done. Tell the owner which checks are missing from the live ruleset. Only the owner runs `apply-repo-settings.sh`, in any mode, `--check` included.

## Release pipeline

Facts come from the consumer's release runbook and spec; check the project's copy first, it wins.

One workflow, `release.yml`, on every push to `main`, one run at a time (concurrency group `release`, nothing cancelled):

1. `release-please` (environment `release-please`) mints a GitHub App installation token with `actions/create-github-app-token` (`permission-contents: write`, `permission-pull-requests: write` only) and runs release-please with it. It must be an App token: PRs, tags and releases made with `GITHUB_TOKEN` start no other workflows, so the release PR would never get its required checks. release-please keeps one release PR open, labelled `autorelease: pending`, that bumps `version.txt` and the changelog. Merging it makes release-please create the tag `vX.Y.Z` and a **draft** release (`"draft": true` and `"force-tag-creation": true` in `release-please-config.json`).
2. `build` (no secrets) runs `scripts/check-release-ref.sh <sha> <tag> <version>` (the tag exists on origin, points at the commit, the commit is an ancestor of `origin/main`, `version.txt` there equals the version), all checks, the R8 release build and the 16 KB alignment check, and uploads the unsigned APK.
3. `smoke` runs the release smoke test on that APK with a throwaway key.
4. `sign-publish` (environment `release`) waits for the release reviewer's approval; nothing is signed before. It decodes the keystore, signs with `scripts/sign-apk.sh`, deletes the keystore, and checks the certificate with `scripts/verify-signature.sh <apk> "$RELEASE_CERT_SHA256"`: `apksigner -J-enable-native-access=ALL-UNNAMED verify -v --print-certs` must print `Verifies` first, `Number of signers: 1`, and a signer SHA-256 equal to the variable. It fails closed when the expected value is empty, not 64 hex characters, or different. Then it writes `<repo name>-<version>.apk.sha256`, attests build provenance with `actions/attest`, and `scripts/publish-release.sh` uploads both files to the draft and publishes it. The asset name comes from `github.event.repository.name`.
5. `verify-published` downloads the published assets and checks the checksum, the signature, `gh attestation verify` and `gh release verify`.

Owner setup (never by an agent, no secret in a command line or a chat): a release key (PKCS12) with an offline encrypted backup; a GitHub App with Contents and Pull requests read and write, Metadata read, installed on this repository only; the secrets `RELEASE_KEYSTORE_BASE64`, `RELEASE_KEYSTORE_PASSWORD`, `RELEASE_KEY_PASSWORD`, `RELEASE_KEY_ALIAS` in the `release` environment and `RELEASE_APP_PRIVATE_KEY` in `release-please`; the variables `RELEASE_APP_CLIENT_ID` and `RELEASE_CERT_SHA256` (64 lowercase hex, no colons). Immutable releases are switched on before the first release, because existing releases stay mutable.

Failure policy:
- A job failed before the release was published: `gh run rerun <id> --failed` only, while the draft is unpublished. Never re-run the whole run: the `release-please` job would find the release already made, report `release_created` false, and every later job would be skipped without an error.
- The `release-please` job failed after it made the tag or draft, an approval was rejected and not re-requested, a deployment waited out its 30 days, or anything failed after publish: the version is burned (immutable releases and the `release-tags` ruleset forbid reusing or moving the tag). Ship the next patch by setting `release-as` to it in `release-please-config.json` in the PR that fixes the cause, and remove `release-as` again after that release.
- A draft older than an hour in `gh release list` means a missing approval or a failed job. Tags are never re-pointed or deleted by hand.

## Dependabot pull requests

A Dependabot PR only starts the work. Before it can merge, add commits that regenerate `gradle/verification-metadata.xml` (`./gradlew --write-verification-metadata sha256 check :app:assembleRelease :checks:check` with a fresh `GRADLE_USER_HOME` and `--refresh-dependencies`; add Linux-only artifacts such as the `aapt2` linux jar by hand after comparing SHA-1 with Google's `.sha1`), update `docs/versions.md`, and fill in Evidence. Strip tool-written comments. There are no bot exceptions. When a new stable AGP or Gradle makes Lint fail every branch (`AndroidGradlePluginVersion`, `GradleDependency`), follow "A new stable release blocks every branch" in the `android-sdlc:sdlc-rules` skill. A Kotlin bump beyond the CodeQL-supported version stays open; the Dependabot template ignores `org.jetbrains.kotlin*` versions above the cap (`">2.4.20"`), so set it to the current cap and move it with the cap.

## Keeping in sync

`${CLAUDE_PLUGIN_ROOT}/scripts/verify-templates.sh <project>` prints one `drift:` line per differing file and `N drift`, exiting 1 on drift. It also compares the `[versions]` entries that both `${CLAUDE_SKILL_DIR}/reference/libs.versions.toml` and the project's `gradle/libs.versions.toml` define, and counts each different version as drift; entries only one side has are ignored.
